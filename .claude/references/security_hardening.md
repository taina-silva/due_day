# Security Hardening & Implementation Reference (security_hardening.md)

This reference outlines the security measures, credential protection standards, native platform configurations, and biometric authentication structures implemented to secure financial and personal data in **DueDay**.

---

## 🔒 1. Credential & State Protection

### 1.1. Google Cloud Platform (GCP) API Key Restrictions
The API keys generated by Firebase for the client applications (found in `firebase_options.dart`) identify the project resources. To prevent abuse, they are restricted in the Google Cloud Console:
1. **Scope Restrictions:**
   - **Android API Key:** Restricted to application package `com.dueday.due_day` and bound to developer debug/upload SHA-1 fingerprints.
   - **iOS API Key:** Restricted to Apple Bundle ID `com.dueday.dueDay`.
2. **API Access Restrictions:**
   - Keys are explicitly restricted to access only essential Firebase services:
     - *Identity Toolkit API* (Firebase Authentication)
     - *Cloud Firestore API* (Database Services)
     - *Firebase Cloud Messaging API* (Notifications)
     - *Firebase Installations API*

### 1.2. Encrypted Local Storage via `flutter_secure_storage`
While the Firebase Auth SDK automatically encrypts user authentication tokens, `flutter_secure_storage` is integrated to handle other highly sensitive parameters:
- **Biometric Preference Encryption:** The toggle preference (`is_biometrics_enabled: true/false`) is saved in secure storage instead of standard plaintext Shared Preferences. This prevents root/jailbreak bypasses where users could edit XML/plist preference files to spoof biometric states.
- **Offline Cache Encryption (Future):** Keys for encrypted databases (e.g. Hive or SQLCipher) must be stored inside the secure storage keychain.

## 🛠️ Native Hardening Configurations

### 1. Android Protection

#### A. Biometric Permissions (`AndroidManifest.xml`)
Required for legacy Android devices (Android 9/API level 28 and lower):
```xml
<uses-permission android:name="android.permission.USE_BIOMETRIC"/>
```

#### B. Screen Capture & Background Privacy (`MainActivity.kt`)
To block screen captures, system video recordings, and recent app previews, the window flags are dynamically configured with `FLAG_SECURE` in the main activity:
```kotlin
import android.view.WindowManager.LayoutParams

override fun configureFlutterEngine(flutterEngine: FlutterEngine) {
    super.configureFlutterEngine(flutterEngine)
    window.addFlags(LayoutParams.FLAG_SECURE)
}
```

---

### 2. iOS Protection

#### A. Biometric Description (`Info.plist`)
Provides user feedback when biometric authentication alerts are triggered:
```xml
<key>NSFaceIDUsageDescription</key>
<string>We require biometric authentication to secure your financial and transaction history.</string>
```

#### B. App Switcher Privacy Blur (`SceneDelegate.swift`)
To prevent visual leakage of account balances or ledger details in the iOS app switcher interface, a native blur filter (`UIVisualEffectView`) is appended to the view window whenever the application leaves the active state:
- **`sceneWillResignActive`:** Adds a visual effect view covering the entire scene window.
- **`sceneDidBecomeActive`:** Removes the covering view from the window structure.

## 💉 Security Services & BLoC Binding

### 1. Security Service (`security_service.dart`)
Wraps the `local_auth` and `flutter_secure_storage` bindings.
- `canAuthenticate()`: Checks device capabilities and system setup.
- `authenticate()`: Triggers native FaceID/fingerprint prompts.
- `isBiometricsEnabled()`: Reads encrypted preferences.
- `setBiometricsEnabled(bool enabled)`: Writes encrypted preferences.

### 2. Global BLoC Injection (`injection_container.dart`)
Registers the biometric authentication service components as singletons:
```dart
sl.registerLazySingleton(() => const FlutterSecureStorage());
sl.registerLazySingleton(() => LocalAuthentication());
sl.registerLazySingleton<SecurityService>(
  () => SecurityServiceImpl(secureStorage: sl(), localAuth: sl()),
);
```

### 3. Biometric Security Block Page (`main_wrapper_page.dart`)
Injects a security listener observing app lifecycle status:
- If biometrics are enabled and the user returns from background state (`AppLifecycleState.resumed`), the layout triggers a blocking overlay screen (`BiometricLockOverlay`) and prompts the native biometric UI.
- The app remains locked under the overlay until biometrics return a successful confirmation.

## ⚡ Verification & Testing Plan

### 1. Screen Capture Blocks (Android)
- Run the Android debug APK, navigate to the Dashboard.
- Try taking a screen capture or screen recording.
- **Success Criteria:** The system blocks the capture action and the app window displays as a solid black layout in the App Switcher.

### 2. App Switcher Privacy Blur (iOS)
- Open the application on an iOS Simulator or real iPhone.
- Swipe up to reveal the App Switcher.
- **Success Criteria:** The snapshot preview of the DueDay app window is obscured by a complete blur filter.

### 3. Biometric Authentication Flows
- **Activation:** Access profile configurations, toggle the biometric switch, and confirm authentication.
- **Background Transition:** Minimize the application and return. Confirm that the security overlay displays instantly and triggers the Touch/FaceID dialog.
- **Cold Boot:** Force close the app via the task switcher and restart. Confirm that the lock overlay covers the splash layout until authentication succeeds.
